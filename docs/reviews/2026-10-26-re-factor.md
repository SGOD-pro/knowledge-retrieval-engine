## Summary
The change completes the bounded integration of the Open Knowledge Framework across Slice 1 and Slice 2. It introduces tenant partitioned storage for entity facts, deterministic CSV table schema extraction, Bedrock extraction with chunk grounding validation, 50ms lookup deadlines, and soft reciprocal rank fusion candidate pooling. Overall architecture and domain modeling are disciplined, with strong multi tenant isolation and ADR-001 fail open decoupling. Changes are requested to resolve per request concurrency controller instantiation that leaks thread pools, unapplied retry disabling on DynamoDB table resources, unpaginated DynamoDB property filtering that risks empty lookups, and legacy caller contract discrepancies that break existing test suites.

## Major
### 🟠 Per request concurrency controller instantiation leaks thread pools and bypasses admission bounds, `backend/src/services/langgraph_pipeline.py:260`
**Problem**: In `run_okf_router`, a new `OkfRetriever` instance is constructed on every single query invocation without passing an existing concurrency controller. `OkfRetriever.__init__` defaults to constructing a new `OkfConcurrencyController`, which creates a new `ThreadPoolExecutor` with four worker threads. Because each query receives an isolated controller and executor, the admission queue bound of eight requests and the concurrency limit of four workers are never shared across concurrent requests.
**Why it matters**: In production under concurrent traffic, storage protection is completely defeated. Worker admission gating will not trigger to protect SQLite or DynamoDB from overload, and active worker thread count will scale with concurrent query volume. In addition, uncollected thread pool executors accumulate unmanaged threads and exhaust system handles.
**Suggested fix**: Provide a singleton accessor such as `get_okf_controller()` that retains a single shared controller across the service lifecycle. Ensure `OkfRetriever` defaults to this shared controller, or update `run_okf_router` to reuse a shared `OkfRetriever` instance.

### 🟠 Retry disabling is not applied to DynamoDB table resource client, `backend/src/db/okf_repo.py:621`
**Problem**: In `DynamoDBOkfRepository._get_resources()`, `disable_client_retries(client)` is called on a low level client instance, but `self._table` is subsequently created via `resource = session.resource(...)`. All repository methods execute against `self._table`, which uses the client attached to the DynamoDB resource (`resource.meta.client`), leaving standard boto3 retries fully active.
**Why it matters**: Acceptance criterion AC-8 requires disabling SDK retries to enforce strict 50ms deadlines. If DynamoDB throttles requests or encounters transient socket hiccups, the underlying SDK client will retry with exponential backoff, delaying the caller far beyond the 50ms deadline and violating the deadline contract.
**Suggested fix**: Call `disable_client_retries(resource.meta.client)` directly after resource creation, or pass the low level client explicitly into the resource constructor via `boto3.resource("dynamodb", client=client)`.

### 🟠 Unpaginated DynamoDB property query risks false empty results, `backend/src/db/okf_repo.py:766`
**Problem**: In `DynamoDBOkfRepository.get_assertions_for_entity`, `FilterExpression = Attr("property_key").eq(norm_k)` is supplied alongside `Limit=limit`. In DynamoDB, `Limit` restricts the number of evaluated items before filter expressions are applied, not the number of returned matching items. Because the query does not loop over `LastEvaluatedKey`, if an entity possesses more items than `limit` and the matching key appears after non matching assertions, DynamoDB returns an empty list.
**Why it matters**: Entities with multiple properties will fail to return valid property assertions when queried by specific property keys in production DynamoDB, causing factual lookups to miss valid index facts.
**Suggested fix**: Either omit `FilterExpression` and filter `property_key` client side over the retrieved slice consistent with how `active_document_ids` is filtered, or paginate using `LastEvaluatedKey` until `limit` items are matched or the partition slice is exhausted within the deadline.

### 🟠 Legacy adapter in OkfRetriever breaks pre existing callers and test suite, `backend/src/services/retrieval/okf_retriever.py:74`
**Problem**: The legacy backward compatibility adapter in `OkfRetriever.lookup()` returns dictionaries with keys `entity`, `property`, and `value`. Pre existing consumers in `evidence_providers/okf_provider.py` and `strategies/okf.py` expect `attribute`, resulting in empty attribute fields in emitted `FactEvidence` and `EvidenceItem` records. In addition, `test_phase3.py` expects `concept` and `property_name`. Furthermore, `OKFStrategy` passes `CloudRepository` into `OKFRetriever`, which raises an `AttributeError` because `CloudRepository` does not implement `resolve_entities`. Running `pytest` fails on `test_cloud_repository_singleton.py` and `test_phase3.py`.
**Why it matters**: Evidence provider records emit empty attributes, strategy lookups fail at runtime, and pre existing test suites in the repository fail, breaking continuous integration.
**Suggested fix**: Include alias keys `attribute`, `concept`, `property_name`, and `property_value` in dictionaries returned by `OkfRetriever.lookup()`. In `OkfRetriever.__init__`, check if the provided repository implements `resolve_entities` before assigning it, falling back to `get_okf_repo()` when `CloudRepository` is passed. Update obsolete test assertions in `test_cloud_repository_singleton.py` and `test_phase3.py` to match the new repository architecture.

## Minor
### 🟡 Behavioral drift in entity resolution between in memory and durable repositories, `backend/src/db/okf_repo.py:190`
**Problem**: `InMemoryOkfRepository.resolve_entities` matches when `cand.startswith(ent_norm)` in addition to `ent_norm.startswith(cand)`. In contrast, `SQLiteOkfRepository` and `DynamoDBOkfRepository` only execute prefix matching where the stored entity name starts with the candidate query string.
**Why it matters**: Tests running against the in memory repository can pass queries where the query string is longer than the entity name, while the same queries fail against SQLite or DynamoDB in production.
**Suggested fix**: Align `InMemoryOkfRepository` with SQLite and DynamoDB by checking only `ent_norm == cand or ent_norm.startswith(cand)`.

### 🟡 Candidate entity token truncation in fallback queries, `backend/src/services/retrieval/okf_lookup.py:90`
**Problem**: In `extract_entity_names_from_query`, step 3 truncates uncapitalized candidate tokens with `filtered[:3]`. If a query contains four or more words before mentioning a lowercase table name such as `financial_summary`, the table name is discarded.
**Why it matters**: Factual queries targeting lowercase table or entity names can fail to resolve the entity if introductory non stop words consume the first three slots.
**Suggested fix**: Allow up to 10 filtered tokens or prioritize tokens containing underscores or digits before applying the slice limit.

### 🟡 Model extraction JSON parser fails on responses with introductory text, `backend/src/ingestion/okf_builder.py:653`
**Problem**: `_parse_model_response` strips leading whitespace and requires markdown code fences to start strictly at index zero. If Bedrock emits any conversational preamble before the markdown code block, markdown fence stripping fails and `json.loads` raises an error.
**Why it matters**: Language model completions that include conversational introductory sentences will fail to parse, resulting in dropped factual extractions.
**Suggested fix**: Use regular expression search to locate the JSON block or array within markdown fences anywhere in the response text.

### 🟡 Weight replacement bug on explicit zero weight in reciprocal rank fusion, `backend/src/services/langgraph_pipeline.py:139`
**Problem**: In `_rrf_merge`, the weight lookup uses `w = getattr(chunk, "okf_weight", None) or okf_weight`. If a caller or chunk explicitly specifies `okf_weight = 0.0` to disable boost for a specific candidate, the truthiness check evaluates zero as false and silently resets the weight to default `1.15`.
**Why it matters**: Explicitly suppressed candidates receive full boost instead of zero weight.
**Suggested fix**: Use an explicit check `w = getattr(chunk, "okf_weight", None); if w is None: w = okf_weight`.

### 🟡 Ingestion batching allows single oversized chunks to exceed the prompt token budget, `backend/src/ingestion/okf_builder.py:384`
**Problem**: In `OkfBuilder._extract_pdf`, if an individual chunk exceeds `max_prompt_chars`, it is still appended to `current_batch` when `current_batch` is empty. The chunk text is not truncated, which can cause the Bedrock call to exceed the 2000 prompt token limit from AC-3.
**Why it matters**: Ingesting documents with unusually large single paragraphs can breach the per call token cap.
**Suggested fix**: Truncate oversized chunk text to `max_prompt_chars` prior to inclusion in model prompt batches.

- Strict adherence to ADR-001 with robust fail open error handling in `DocumentsService` and `langgraph_pipeline`, ensuring that OKF extraction or retrieval failures never degrade baseline retrieval.
- Grounding verification in `is_value_grounded` correctly validates verbatim token sequences and normalized numbers against source chunks, preventing hallucinated assertions from entering storage.
- Comprehensive test suites in `test_okf_slice1.py` and `test_okf_ablation_slice2.py` with 34 focused unit and ablation tests covering counterexample preservation, ambiguity splitting, and tombstone isolation.
- Tenant isolation enforced strictly at the database partition key level (`WORKSPACE#{workspace_id}`), preventing cross tenant leakage by construction.
