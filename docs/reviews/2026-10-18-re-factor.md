## Minor
### 🟡 Substring matching in aggregate operator selection, `backend/src/services/retrieval/structured_query_service.py:1093`
**Problem**: In `_execute_aggregate`, aggregate operator selection uses simple substring checks such as `"count" in q_lower` and `"min" in q_lower` without word boundaries.
**Why it matters**: If a query references columns or entities containing these substrings (such as "discount", "account", or "admin"), `"count" in q_lower` or `"min" in q_lower` evaluates to true, causing sum or average queries to execute as count or min operations in production.
**Suggested fix**: Use word boundary regular expressions matching exact operator keywords (such as `re.search(r'\bcount\b', q_lower)`) when selecting `AggregateOp`.

### 🟡 Substring containment in column name resolution, `backend/src/services/retrieval/structured_query_service.py:381`
**Problem**: In `_find_target_metric_column`, column resolution checks `col.name.lower() in q_lower` without word boundary constraints.
**Why it matters**: Short column names such as "id", "tax", "rate", or "net" can match substrings inside common conversational words (such as "id" in "did", or "rate" in "corporate"), causing metric selection to latch onto an identifier or unrelated column instead of the intended numeric metric.
**Suggested fix**: Use word boundary regular expression matching `re.search(rf"\b{re.escape(col.name.lower())}\b", q_lower)` instead of substring containment `col.name.lower() in q_lower`.

### 🟡 Multiple year predicates conjoined with logical AND, `backend/src/services/retrieval/structured_query_service.py:494`
**Problem**: When an aggregate query contains multiple four digit years, `_extract_and_bind_predicates` appends an equality predicate for each year on the temporal column.
**Why it matters**: Because table store backends evaluate predicates conjunctively, no row can have a year equal to multiple distinct years simultaneously, returning zero rows for multi year aggregate requests.
**Suggested fix**: When multiple years are present in an aggregate query, bind a single predicate using `PredicateOp.IN` with the collection of years, or reject unsupported multi year aggregations prior to store execution.

## Resolution of review findings
All three minors and nit 1 were resolved:
1. Aggregate operator selection in `_execute_aggregate` uses word boundary regular expressions matching exact operator keywords (`\bcount\b`, `\b(?:sum|total)\b`, `\b(?:average|avg)\b`, `\b(?:min|minimum)\b`, `\b(?:max|maximum)\b`), preventing substring collisions from terms like discount or admin.
2. Column name resolution in `_find_target_metric_column` requires word boundary regular expression matching `re.search(rf"\b{re.escape(col.name.lower())}\b", q_lower)`, preventing short column identifiers from matching within longer words.
3. Multi year filter extraction in `_extract_and_bind_predicates` binds `PredicateOp.IN` when multiple four digit years are specified, verified by regression test `test_multiple_years_bind_with_in_predicate`.
4. Nit 1 resolved: temporal column exclusion in `_execute_aggregate` uses set comprehension `{c.col_index for c in schema.columns if ...}`, excluding all temporal columns.
