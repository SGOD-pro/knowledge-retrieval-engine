## Summary

This change implements Open Knowledge Framework (OKF) Slice 3.1, providing durable extraction budget ledger coordination across memory, SQLite, and DynamoDB stores, monotonic fence tokens, a 15 second lease expiry, in-flight attempt manifest persistence, and authoritative provider token bounding via Bedrock Runtime `count_tokens`. The multi-process SQLite test suite proves that physical dispatches across concurrent processes are bounded to the two call ceiling, and retries acquire separate durable reservations. However, code inspection reveals two Major correctness discrepancies: DynamoDB budget recovery fails to check legacy manifests when no budget ledger item exists, and failed status handling is inconsistent between DynamoDB and local repositories.

## Major

### 🟠 Legacy manifest recovery in DynamoDB is bypassed when no budget ledger item exists, [`backend/src/db/okf_repo.py:2071-2073`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L2071-L2073) and [`backend/src/ingestion/okf_builder.py:268-283`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/ingestion/okf_builder.py#L268-L283)
**Problem**: In [`DynamoDBOkfRepository.get_budget_ledger`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L2055-L2111), if no budget record exists in table `kre_okf_facts` under `SK = BUDGET#DOC#{doc}#VER#{ver}`, the method immediately returns `None` without checking [`DynamoDBOkfRepository.get_manifest`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1714-L1729). In [`get_or_create_document_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/ingestion/okf_builder.py#L250-L294), the check for `get_budget_ledger` and `get_manifest` is structured as mutually exclusive `elif` branches. Because [`DynamoDBOkfRepository`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1440) implements `get_budget_ledger`, the subsequent `elif hasattr(repo, "get_manifest")` branch is skipped entirely when `get_budget_ledger` returns `None`.
**Why it matters**: For any document version previously ingested before Slice 3.1, or any version where a crash persisted an in-flight failed manifest before creating a ledger record, `get_or_create_document_budget` finds no ledger, skips reading the manifest, and initializes a fresh extraction budget with zero prior calls. This permits re-extraction on already exhausted or failed documents in production DynamoDB, defeating crash recovery and duplicate call bounding.
**Suggested fix**: Update [`DynamoDBOkfRepository.get_budget_ledger`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L2055-L2111) to query [`DynamoDBOkfRepository.get_manifest`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1714-L1729) when no budget item is found (matching the fallback behaviour already present in [`InMemoryOkfRepository`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L690-L700) and [`SQLiteOkfRepository`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1410-L1425)). In addition, update [`get_or_create_document_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/ingestion/okf_builder.py#L268-L283) so that `repo.get_manifest` is evaluated whenever `ledger is None`.

### 🟠 Inconsistent handling of failed ledger status across repository implementations, [`backend/src/db/okf_repo.py:421-438`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L421-L438) and [`backend/src/db/okf_repo.py:1042-1060`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1042-L1060)
**Problem**: In [`DynamoDBOkfRepository.reserve_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1759-L1783), the condition expression requires `#st = :st_act` (`status = "active"`). When a ledger's status is `"failed"`, DynamoDB correctly fails the condition check and denies further reservations. However, in [`InMemoryOkfRepository.reserve_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L421-L438) and [`SQLiteOkfRepository.reserve_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1042-L1060), the reservation logic checks only for `"completed"` and `"exhausted"`. If status is `"failed"`, both InMemory and SQLite allow the reservation to succeed and overwrite the status back to `"active"`. Furthermore, [`ExtractionReservationResult`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/schemas/contracts/okf.py#L152-L170) does not define a reason for failed status (such as `"already_failed"`), causing DynamoDB error handling to fall through to `"calls_exhausted"`.
**Why it matters**: Local repository tests diverge from DynamoDB cloud semantics. A document version marked `"failed"` in SQLite or Memory can continue to acquire call permits up to `max_calls`, whereas in DynamoDB it is strictly rejected.
**Suggested fix**: Add an explicit check for `ledger.status in ("completed", "exhausted", "failed")` in [`InMemoryOkfRepository.reserve_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L421-L438) and [`SQLiteOkfRepository.reserve_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1042-L1060), and add `"already_failed"` to [`ExtractionReservationResult.reason`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/schemas/contracts/okf.py#L160-L168) so all backends report identical rejection reasons.

### 🟡 Contradiction between specification prose and implementation regarding throttling retry reservations, [`docs/specs/0006-okf-integration.md:38`](file:///home/swyra/projects/knowledge-retrieval-engine/docs/specs/0006-okf-integration.md#L38) and [`docs/specs/0007-knowledge-graph-enrichment.md:241`](file:///home/swyra/projects/knowledge-retrieval-engine/docs/specs/0007-knowledge-graph-enrichment.md#L241)
**Problem**: The prose in specification 0006 (`docs/specs/0006-okf-integration.md:38`) states that throttling retries "reuse the active lease permit without creating unreserved calls", and specification 0007 (`docs/specs/0007-knowledge-graph-enrichment.md:241`) states that "A retry reuses the active reservation slot". However, commit `a7cc4b2` and verification document [`docs/specs/0006-verify.md`](file:///home/swyra/projects/knowledge-retrieval-engine/docs/specs/0006-verify.md) enforce that every physical dispatch attempt, including throttling retries, acquires a separate atomic durable reservation on the ledger (`reserved_calls` increments from 1 to 2).
**Why it matters**: Engineers implementing downstream graph enrichment or auditing the system against the specs will encounter conflicting requirements between the prose (reusing a single reservation slot) and the code and verification document (acquiring a separate durable reservation per attempt).
**Suggested fix**: Update the prose in [`docs/specs/0006-okf-integration.md`](file:///home/swyra/projects/knowledge-retrieval-engine/docs/specs/0006-okf-integration.md) and [`docs/specs/0007-knowledge-graph-enrichment.md`](file:///home/swyra/projects/knowledge-retrieval-engine/docs/specs/0007-knowledge-graph-enrichment.md) to state clearly that throttling retries acquire a separate atomic durable reservation while reusing the active lease owner identity.

### 🟡 Fenced token spend update in DynamoDB references non-existent attribute without default, [`backend/src/db/okf_repo.py:1981-1985`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1981-L1985)
**Problem**: In [`DynamoDBOkfRepository.reconcile_extraction_budget`](file:///home/swyra/projects/knowledge-retrieval-engine/backend/src/db/okf_repo.py#L1981-L1985), the fallback update for recording fenced token spend uses `UpdateExpression="SET #spent = #spent + :actual_tokens, ..."` without `if_not_exists(#spent, :zero)`.
**Why it matters**: If a fenced reconciliation occurs on an item where `spent_tokens` was never populated or the item was partially created, DynamoDB raises a `ValidationException`. Although caught and logged, the fenced token spend is dropped.
**Suggested fix**: Change the expression to `#spent = if_not_exists(#spent, :zero) + :actual_tokens` to ensure safe arithmetic.
