# 0004: Core engine walking skeleton and benchmarks

**Status**: In Progress

## Summary
This spec outlines the next milestone: a bounded core engine walking skeleton that proves the complete path works end to end. It establishes real document ingestion with provenance, structured data execution, hybrid retrieval, and evidence-backed answers, all validated by reproducible benchmarks for correctness and latency. Advanced distributed features are deferred.

## Requirements
AC-1: The skeleton operates within one development workspace, validating existing identity and access checks without bypassing boundaries.
AC-2: Ingestion handles real CSV and text PDF files, building embeddings at ingestion and persisting source/version provenance in DynamoDB.
AC-3: Ingestion supports partial failures (e.g. unreadable pages), continuing to process while recording exact exclusions and incomplete coverage flags.
AC-4: Structured execution processes full datasets (no row truncation) using typed, restricted lookup, filter, and aggregation operations.
AC-5: Retrieval executes BM25 and baseline vector searches, followed by bounded reranking.
AC-6: Answers are assembled from verified evidence, including citations. If unaffected evidence supports an answer, it is permitted.
AC-7: Complete aggregate claims are explicitly blocked when required dataset coverage is incomplete, reporting insufficiency.
AC-8: If evidence is insufficient, the system returns a graceful 200 OK with a structured refusal and empty citations; infrastructure failures remain distinct (503).
AC-9: A reproducible benchmark runner measures and reports correctness, evidence support, coverage, token usage, ingestion time, and query latency.
AC-10: Compact benchmark-run metadata is persisted in DynamoDB as scoped records, and detailed versioned JSON artifacts are stored in S3 using a recoverable write sequence (S3 first, then DynamoDB) rather than claiming atomic 1:1 persistence.
AC-11: Deterministic correctness and regression checks are verified via `pytest`.

## Decision
We will build a Tracer Bullet vertical slice that connects the full retrieval-augmented generation pipeline. We are using the existing stack (FastAPI, DynamoDB, Qdrant, Redis) and existing workspace boundaries. Ingestion provenance and benchmark summaries will be stored as separate DynamoDB records, preventing workspace attribute bloat, with detailed benchmark artifacts pushed to S3. Partial ingestion is explicitly permitted but tracked, enabling robust query responses that downgrade gracefully rather than failing entirely.

## Feature design

**Data model sketch**:
| Entity | Key Fields | Relationships | Notes |
|---|---|---|---|
| Workspace | id, name, created_at | (existing) | Core boundary |
| DocumentSnapshot | workspace_id (PK), document_id (SK), source, version, format, incomplete_coverage_flag, exclusions | Belongs to Workspace | Stores provenance and coverage |
| BenchmarkRunMetadata | benchmark_run_id (PK), workspace_id, timestamp, latency_ms, token_usage, status | Belongs to Workspace | Compact summary |
| BenchmarkArtifact (S3) | s3_key (benchmark_run_id.json) | Related to BenchmarkRunMetadata | Detailed JSON reports |

*Persistence Details for Bounded Slice*:
- **Full CSV datasets**: Stored in S3 (or local mock S3) bound to `source` and `version`.
- **PDF chunks & Vector bindings**: Persisted in Qdrant collections scoped by workspace.
- **BM25 indexes**: Persisted in local disk / Redis with pointers stored in DynamoDB `DocumentSnapshot`.
- **Version selection**: Queries select the highest ready `version` for a given `source` directly via the `DocumentSnapshot` registry, bypassing 0003's complex distributed GC and publication logic.

**API surface & Contract Extensions**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/api/v1/workspaces/{ws_id}/documents` | POST | multipart file (CSV/PDF) | `document_id`, `version`, `incomplete_coverage_flag` | bearer | 400 invalid format, 413 payload too large |
| `/api/v1/workspaces/{ws_id}/query` | POST | `QueryContract` | Answers, citations, refusal flag | bearer | 503 infrastructure failure |

*Contract extensions*:
- Extend `QueryContract` with `target_source_version` to explicitly route queries to a ready version.
- Extend `CanonicalEvidence` with `exclusion_flags` to explicitly track when evidence is drawn from partially ingested sources.
- Extend `CapabilityArtifact` to handle typed structured operations (e.g. `sum`, `count`, `filter` on specific columns).

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| Ingest | source/version provenance | Extracted from file metadata/hash during ingestion |
| Ingest | incomplete coverage flag | Computed by parser when skipping malformed rows/pages |
| Query | structured refusal / citations | Generated by answer assembly when verified evidence is insufficient |
| Benchmark | token usage, latency | Measured directly by the benchmark runner wrapper |

**Key invariants & Coverage Semantics**:
- Cache hits or query executions never cross workspace boundaries (enforced by AC-1).
- Benchmark persistence is recoverable: S3 artifacts are written before DynamoDB metadata. Orphan S3 objects are acceptable on partial failure; missing S3 objects for committed DynamoDB records are not.
- **Coverage Semantics**: Complete aggregate claims (e.g. "total revenue for the year") over a dataset with `incomplete_coverage_flag = true` must explicitly refuse to answer. However, explicitly scoped operations over verified covered data (e.g. "total revenue for Q1", where Q1 rows are verified intact) are permitted.

**Security model**:
All operations execute within the existing workspace boundary model. Benchmark artifacts stored in S3 are scoped by workspace identity, preventing cross-tenant leakage of evaluation data.

**Configuration required**:
- `S3_BENCHMARK_BUCKET`: The S3 bucket name for storing detailed JSON benchmark artifacts.
- `BENCHMARK_RUNNER_ENABLED`: Boolean flag to enable/disable the heavy benchmark suite in CI/CD.

**Critical test scenarios & Reproducible Pytest Execution**:
- Happy path: A PDF is ingested successfully, and a query returns a correct, cited answer within budget. Verifies AC-2, AC-5, AC-6.
- Partial failure: A CSV with malformed rows is ingested; an aggregate sum over the *entire* dataset is blocked, but a sum over the intact rows succeeds. Verifies AC-3, AC-7.
- Insufficient evidence: A query for an unknown fact returns a 200 OK structured refusal, whereas pulling the database offline returns a 503. Verifies AC-8.
- Boundary enforcement: Test credentials attempt to query a different workspace's ingested documents and receive a 404. Verifies AC-1.

*Reproducible Execution*:
- **Deterministic regression checks**: Run via `pytest` using mocked LLM responses and local test fixtures to verify routing, authorization, and boundaries without network overhead.
- **Benchmark runner**: A separate test suite using a fixed corpus/question set, fixed configuration versions, and real embedding/reranker/generation runs. Measures exact correctness/evidence metrics, timing boundaries, and token accounting. Ground truth is strictly segregated from engine inputs.

## Consequences
- **Pros**: Proves the complete execution path end to end; isolates heavy benchmark data in S3; robustly handles dirty ingestion without failing completely.
- **Cons**: Requires managing dual persistence (DynamoDB + S3) for benchmarks; partial ingestion adds complexity to the query verification logic (aggregate blockers).

## Implementation Order & Blockers

**0002 Reconciliation & Blockers**:
While Spec 0002 is marked complete and reported tests pass (e.g. `test_fix7_idor_regression.py`), independently run `/check review` identified concrete blockers that must be resolved before executing 0004:
1. `backend/src/api/workspace_boundary_routes.py` hardcodes test fixtures (`ControlledFixtureExecutionEngine`, `InMemoryCacheStore`), completely bypassing the actual retrieval pipeline.
2. `backend/src/db/table_store/dynamodb_store.py` uses synchronous `time.sleep` in its retry loop, which will block the FastAPI ASGI event loop.
3. Missing `sys.path` injection in `test_fix7_idor_regression.py`.

**Order of implementation (First Bounded Development Step)**:
1. Resolve the 0002 production wiring blockers (remove fixtures from routes, fix async sleep).
2. The smallest real CSV/PDF end-to-end slice: Ingest one CSV/PDF, persist to Qdrant/local storage, and execute a single end-to-end query via `pytest`.
3. Broaden structured coverage (aggregation, filtering) and implement the benchmark runner suite.
4. Defer PageIndex, OKF, graph, LAYA, and distributed publication (0003) to later phases.

## Rationale
Building a Tracer Bullet walking skeleton proves that the complex multi-step orchestration (ingestion, vector/BM25 retrieval, structured execution, and reranking) works coherently before adding scaling optimizations. Separating benchmark metadata (DynamoDB) from bulk artifacts (S3) keeps the database lean while preserving rich evaluation history. Permitting partial ingestion reflects real-world messy data, and the strict aggregate blocking prevents dangerous AI hallucinations.
